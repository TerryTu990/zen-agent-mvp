# 2026-09-07 发布后试用排查汇总：问题、根因与优化建议

> 类型：计划（人读层）。裁决权在 Terry；本文只给事实、根因与建议，不代替裁决。
> 来源：服务端快照 2.2.0 / 插件 0.12.0 发布后，Terry 的真实试用与三条服务端会话审计，
> 以及随后就「后台页能否被读取」「面板能否默认展示」两问做的代码核对。
> 上一轮的根因与方案见 `2026-09-07-task-auth-and-ux-round.md`；本文是它之后的第二批发现。

## 0. 结论速览

六个事项。一条是正确性风险，四条是用户可见的错误或困惑，一条是浏览器硬限制。
另有两件经核对确认**无需改动**，一并记下以免下次重复排查。

| 编号 | 事项 | 类别 | 建议优先级 |
|---|---|---|---|
| F1 | 缺省活跃页的 dom 批次不钉页面身份，活跃页在快照与执行之间切换即落错页 | 正确性 | P0 |
| F2 | 空白页上出现点下去必然解析不出的「总结本页」入口 | 用户可见的错 | P1 |
| F3 | 仅基座轮里模型误判「平台没有页面能力」而拒绝真实任务 | 模型稳定性 | P2 |
| F4 | agent 新开页上侧边栏被 Chrome 关闭，须再点一次图标 | 用户可见的惑 | P1 |
| F5 | 站点访问权限授予后不补注入，已失败的页要等重载 | 用户可见的惑 | P1 |
| F6 | 注入失败对用户零信号，`silent` 页读不了但看不出原因 | 用户可见的惑 | P1 |

## 2. 事项详述

### F1 缺省活跃页的 dom 批次不钉页面身份（正确性，P0）

**现象**：`37443e19` 里出现一张「未成功：browse.page-operate」卡，卡上无原因，任务本身完成。

**审计事实**：该次调用裁决为 allow，执行 35 毫秒后返回 error，回喂内容是
`{"error":"step-1-click:ref-not-found"}`。审计里这次调用的页面归属是腾讯云文章页，
而它前两次成功调用的归属都是百度页。

**根因**：agent 点击百度结果链接成功，文章在新标签页打开。它随后取的快照仍是百度页，
于是判断「没跳转成功」，用同一个 `za-165` 重试点击。指令下发时活跃页已切到文章页，
`za-165` 属于百度快照，文章页的引用表里没有它，客户端在动作发生前返回找不到元素。

机制上的缺口有两层：

- **签发侧不钉落点**。`packages/toolgate/src/index.ts` 的 dom 签发分支里，
  `expectedPageUrl` 只在解析出定向目标时才写入指令。缺省作用于活跃页的批次不带任何页面身份，
  客户端 `apps/extension/src/delegated-execution.ts` 的逐字段比对因此全部跳过。
- **裁决侧不校验来源页**。`DomGateContext` 已经携带快照页的 `origin` 与 `path`
  （`packages/contracts/src/ports.ts`），但 `validateDomSteps` 只用它做围栏与引用闭集判定，
  不比对「产出这批引用的那一页」是否仍是当前活跃页。

**影响**：这次是安全的，因为落点页当时还没取过快照、引用表为空，所以必然落空。
但引用编号是每份快照内的顺序编号，跨页不通用且会重号。若落点页此前取过快照且元素数足够，
同名引用会解析到另一页上的另一个元素，点击就会落在意料之外的地方。
**安全是运气，不是设计保证**，这是本批唯一的正确性风险。

**建议**：

1. 裁决时以服务端自持事实比对：`domContext` 的来源页与当前活跃页不一致即拒签，
   回喂「页面已变化，请重新快照后再操作」。这是 fail-closed 前置，落点在 toolgate。
2. 签发缺省批次时同样钉页面身份，客户端不符即返回 `context-mismatch`。这是执行侧兜底，
   与既有定向批次共用同一条比对逻辑。
3. 面板失败卡补一行原因。现在用户只看到「未成功」，看不到为什么。

### F2 空白页上出现不可解析的快捷提问（用户可见的错，P1）

**现象**：在 `chrome://newtab` 上点击「总结本页」，agent 回答无法总结本页。

**审计事实**：装配事件带 `quickActionId: summarize-page` 且 `quickActionUnresolved: true`。
送进模型的用户轮消息是 chip 的标签原文「总结本页」，不是站点包声明的模板。

**根因**：该快捷提问由通用站点包声明，而通用包只在页面有 http 或 https 来源时激活。
`chrome://newtab` 没有可用来源，服务端本轮 packId 为空，模板查不到，
于是按 `apps/server/src/quick-actions.ts` 的设计回退成原文并在审计里标记未解析。
服务端这一步是如实的，问题在前一步：`apps/extension/src/background.ts` 的 `quickActionScope`
在会话尚未建立时无条件按通用包渲染 chips，不判断当前页是否可激活。
更糟的是 Chrome 内部页永远不会产生页面上下文上报，这排错误的 chips 在这类页面上不会被后续刷新收窄。

这与该函数上方注释写的「宁可少给入口，也不给一条点下去会被服务端按未知 id 回退的 chip」正好相反。

**建议**：

1. 无会话时先看活动标签页地址，非 http 或 https 一律不给通用包 chips。改动很小。
2. 未解析的快捷提问不再静默按原文下发；面板给一句「本页没有可用的快捷提问」，
   而不是把 chip 标签当成用户提问送进模型。

### F3 仅基座轮的误拒（模型稳定性，P2）

**现象**：`ec810dd7` 第二轮，Terry 发了完整的百度搜索任务，模型直接拒绝，
称当前环境没有注入页面读取与操作工具，任务无法完成。

**事实**：当时 `open_url` 是注入了的，模型自己也承认「我能用的只有通用网页打开与个人配置草稿功能」。
一分钟后的 `0dd74437` 从同样的空白页冷启动、同样一句任务，完整走完了打开、搜索、开文章、总结的全链路。

**根因**：模型行为不稳定，并被上下文自我强化。第一轮那句「看不到页面内容」如实但只对那一轮成立，
它留在历史里，成了第二轮拒绝的依据。而第一轮之所以发生，是 F2 触发的。
所以两件事有因果链：错误的 chip 引出一轮仅基座对话，模型在那一轮的诚实自述又毒化了下一轮的真实任务。

**建议**：在基座补一条指引，明确当前页不可读时，若任务需要网页内容，
应先用 `open_url` 打开目标页，工具面会随落点换出，不得据此判定任务不可完成。
这条改 `assets/`，须跑评测并升快照版本。

### F4 agent 新开页上侧边栏被关闭（用户可见的惑，P1）

**现象**：分组内先开百度、再开 B、C 页，切到 B、C 时对话面板不显示，须再点一次扩展图标。

**根因**：面板全局默认禁用，只对任务组内的标签页逐个启用。Chrome 的行为是：
切到一个面板处于禁用状态的标签页即关闭侧边栏，之后切回启用的标签页不会自动重开，
重开只能调用打开接口，而该接口必须在用户手势内调用。触发关闭的窗口有两个：

- `apps/extension/src/background.ts` 没有监听标签页创建事件。新页只在被激活或分组变更时才启用，
  而 agent 开页是创建、入组、激活的异步序列，存在「已成为活跃页但尚未启用」的瞬间。
- 扩展后台脚本被浏览器回收重启时会重跑一次全局禁用。此后新开的标签页没有逐页设置，
  落回全局禁用，同样会被关闭。

**建议**：

1. 在开页逻辑里入组之后、设为活跃之前，先把该标签页的面板置为启用；
   再补一个标签页创建事件的监听，对由组内页面打开的新页同样提前启用。
   切过去时面板已是启用状态，Chrome 就不会关，表现即「面板一直在、会话连续」。风险低。
2. 可选的更彻底方案是反转默认：全局启用并给路径，只对组外标签页显式禁用，竞态从根上消失。
   代价是面板在任意页面都可用，用户能从 Chrome 侧边栏菜单打开 Zen，
   与「面板只在任务组内出现」的现有口径有出入，须 Terry 裁决。

**硬限制**：面板本来没开时，agent 开新页不可能让它自动弹出。Chrome 不允许无用户手势打开侧边栏。

### F5 权限授予后不补注入（用户可见的惑，P1）

**根因**：`apps/extension/src/` 下没有监听浏览器权限变更事件。
某页若因缺少站点访问权限而注入失败，用户随后在扩展设置里授予权限时，该页不会自动补注入，
要等它重新加载或被重新激活。

**建议**：监听权限授予事件，一旦拿到新的站点访问权限，就对当前所有任务组内的标签页扫一遍补注入。

### F6 注入失败对用户零信号（用户可见的惑，P1）

**先澄清 `silent` 的语义**，因为它容易被误读成「另一类会员身份」：

一个分组一个会话，组内每个页面都应该接入，这既是产品口径也是代码实现的意图。
触发注入的地方有五处，覆盖了所有进入分组的路径：点击图标、页面加载完成且所属分组是 zen 组、
标签页被拖入已映射的分组、agent 导航开页、内容脚本自身的握手。
`silent` 不是第三种成员身份，它是一句如实报告：这一页在组里，但执行器没能放进去。
必须报出来，是因为签发指令前要 fail-closed，把读不了的页说成能读会让 agent 发出必然超时的读取。

现在还会落到 `silent` 的只有四种情况：

| 情况 | 可否消除 |
|---|---|
| 浏览器不允许注入的页，如 `chrome://` 开头的页、扩展商店、PDF 阅读器、`view-source` | 不可，浏览器硬限制 |
| 该站点访问权限没拿到 | 0.12.0 已在首次批准时申请；用户当时拒绝则仍进不去，可由 F5 缓解 |
| 采样时页面还在加载，注入或端口连接尚未落地 | 瞬时，下一次清单上报即转为 background |
| 用户自己把站点加进了不辅助名单 | 故意行为，不应消除 |

**缺口**：`adr-027` §4 明确接受了「注入失败不产生任何客户端信号」这一取舍。
结果是用户只看到某页读不了，不知道为什么，也不知道能做什么。

**建议**：在面板的页面清单里给 `silent` 页标注原因，并提供一个「让 Zen 接入这一页」的按钮，
点击即是一次带用户手势的注入重试。这同时给了 F5 一个手动兜底。

## 3. 经核对确认无需改动的两件事

- **定向读取后台页的能力已具备**。`page_snapshot` 是平台内建工具，可定向读取组内 active 与 background 页，
  只有 `silent` 被拒。人工把活跃页切回百度后，被读页降为 background，仍在放行范围内，
  观测首行带来源页标注。真正的瓶颈是模型必须显式传 `targetPage`，不传就读成活跃页，
  这与 F1 同源，建议在通用包功能规则里一并补一条指引。
- **内容脚本端口断开会自动重连**，退避三百毫秒。扩展后台被浏览器回收不会让已接入的后台页永久掉线。

## 4. 建议的批次与优先级

| 批次 | 内容 | 触及面 |
|---|---|---|
| 第一批（P0） | F1 的裁决侧来源页校验与签发侧页面身份 | toolgate、gateway、插件执行侧、单测 |
| 第二批（P1） | F2 chips 收窄、F4 面板提前启用、F5 权限授予后补注入、F6 silent 原因与手动接入按钮 | 插件、面板、单测 |
| 第三批（P2） | F3 基座指引、F1 与后台页读取的 `targetPage` 指引、F1 失败卡原因 | `assets/`、面板 |

第三批触及 `assets/`，须跑评测并升快照版本，因此建议单独成批、单独发布。

## 5. 验证要求

- 每条修复都要有能证伪的测试，不接受只靠人工复跑。
- F1 应有单测覆盖「快照来源页与活跃页不一致即拒签」，并在浏览器 E2E 里复现活跃页切换的时序。
- F5 与 F6 可复用本轮 E2E 改造引入的 scoped 授权夹具，
  它能造出真实的「未授权导致注入失败」形态，见 `scripts/e2e/run-nav-attach.mjs`。
- 改 `assets/` 后按 `ZA-C-EVAL-01` 跑评测不少于三跑，并同步升 `assets/manifest.json` 版本与快照版本钉。
- 收口用 `pnpm test:e2e:family` 跑完整家族，落盘报告可从磁盘复核。
